# Mycelium Extra — Target Architecture and Development Principles

## 1. Target architecture

Owners: lineage, report values, review tripwires, ingest provenance and memory are **Mycelium's**; plan, approval,
receipts, output declarations and verify are **Extra's**. See `G13`.

# 2. Core design principles

## G1 — Evidence for Extra's own claims before breadth

Extra claims three things: it surfaces consequential choices before code runs; only approved plans run; and it reports
honestly what ran against the plan, with low friction. Test those before adding features. Whether Extra reduces
scientific errors compared with no Extra is a separate research question (Track R in `03`), not a package gate.

## G2 — A gap never becomes a pass

Unavailable, ambiguous, or incomplete evidence must remain visible.

## G3 — Execution conformance is not scientific correctness

Keep separate concepts for:

```text
scientific intent
scientific implementation
execution provenance
reported claims
```

## G4 — Keep human-readable reasoning primary

Do not replace Markdown planning with a large DSL.

Preferred design:

```text
human-readable plan
        +
small machine-readable contract
```

## G5 — Automate high-value invariants

Prioritize machine-checkable properties such as:

- sample alignment;
- contrast direction;
- biological unit;
- matrix state;
- reference identity;
- output completeness.

Do not attempt universal automated scientific judgment.

## G6 — Prefer deterministic evidence over inference

Prefer:

```text
explicitly generated by run X
```

over:

```text
probably generated by run X
```

## G7 — Derive state where possible

Before adding a persistent state file, ask whether the information can be reconstructed from:

- git;
- plans;
- receipts;
- provenance;
- contracts.

## G8 — Minimize visible concepts

Users see the usage tiers (plan; run with approval; verify reportable work; full project workflow), which already read
as plan → run → check. Do not add routing skills: Mycelium routes by intent. Simplify wording; keep advanced
capabilities expert-facing.

## G9 — Known failures drive the roadmap

Observed and reproducible failures take priority over hypothetical safeguards.

## G11 — Repository constraints bind every task

Python 3.6 and stdlib only for hooks and skill scripts; an optional reader (`h5py`, `Rscript`) is detected and its
absence is a gap; friction is opt-in and off by default; complement Mycelium and never override it (clashes go to the
user); no SessionStart messages; plain-text hook notices; one feature = two commits; `hooks/tests/gate_diff.py`
before and after any `gate.py` change.

## G12 — Reactivation needs evidence

Parked work returns only on the conditions in `05_PARKED_AND_NON_GOALS.md`, and a task without a demonstrated failure
or requirement is parked rather than scheduled.

## G13 — Consume Mycelium first

Extra adds only what Mycelium lacks. Where Mycelium already records something, Extra reads that record and builds the
link to the plan and approval; its own mechanism is a **fallback** for plain repositories (Extra works without
Mycelium, `docs/mycelium-integration.md:5-7`), reported as weaker evidence or a gap.

| Mycelium owns (0.7.2) | Source | Extra's role |
|---|---|---|
| Memory: decisions, learnings, findings | `.living/` | reads for grill; confirmed appends only |
| Run lineage: script, inputs and outputs with SHA-256, exit, per session | `.living/log/data-lineage/<session>.json` (`extract_data_lineage.py`; python / R / jupyter; written at Stop) | joins to receipts; own fingerprints for sbatch, workflow managers, plain shell |
| Report values | `register_value` → `outputs/numbers.json` → report manifest → scitexlintr | the claims block is the plan-linked fallback; adds a `direction` kind |
| Review tripwires | `mycelium:review` (known-answer, metamorphic, fault-injection) | plan carries the tripwire spec; verify reports whether one ran |
| Ingest provenance | `data/DATA_MANIFEST.md`, `provenance.md` (SHA256) | verify compares pinned inputs against it |
| Routing by intent | `analyze`, `review`, `report`, `ideas`, `ingest` | none; no routing skills |

Known limits of what is consumed: Mycelium's lineage covers python, R and jupyter, not `sbatch`, `snakemake` or
`nextflow`, and is written when the session stops, so verify inside the same session may find it absent. Absent is a
gap, never a pass.

Extra does not judge scientific correctness. That remains Mycelium's `review` plus the researcher.

## G10 — Preserve known misses

Known-miss tests should remain in the suite until fixed.

When fixed, invert their expected behavior rather than deleting their history.

# 3. The plan's Choice block (the "scientific contract")

Not a separate schema layer. It is a small structured block inside grill's plan, in the same Choice cells the plan
already has, covering: biological unit, pairing, contrast (numerator, denominator, `positive_means`), sample key,
matrix state, reference level.

It should:

- contain only established values and allow `unknown`;
- freeze with the approved plan;
- be validated by a hand-written stdlib check;
- feed `data-contract-check` on the input side rather than duplicate it;
- express a declared direction as a **tripwire specification** that Mycelium's `review` can run.

Detecting a reversed contrast in arbitrary analysis code is not mechanical. Only declared-direction outputs and claims
are checked; the rest is `HUMAN_REVIEW_REQUIRED`. It must not become a general statistical language.

---

# 4. Generic output integrity versus the Choice block

These are separate layers.

## Generic output integrity

Implemented as an extension of `data-contract-check` applied to plan-declared outputs, not a new checker.

Answers:

> Is the expected artifact structurally complete?

Example:

```yaml
path: outputs/de.tsv
required: true
checks:
  required_columns:
    - gene
    - log2fc
    - padj
  minimum_rows: 100
```

## Plan Choice block

Answers:

> Does the analysis respect declared scientific intent?

Example:

```yaml
unit:
  biological: participant

contrast:
  numerator: day28
  denominator: baseline
  positive_means: higher_day28

sample_alignment:
  key: sample_id
  positional_matching_allowed: false
```

The Choice block may reference generic output-integrity specifications, but should not redefine them.

# 5. Execution modes

These are the existing usage tiers, named; no new concept is added. `explore` = recorded, non-reportable runs.
`approved` = tier 2 (approved plan, gate, receipts). `reportable` = tier 3 (approved plan, frozen code, pinned
inputs, `verify`).

## Explore

- rapid;
- non-reportable;
- recorded as exploratory;
- outputs cannot be promoted without re-run.

## Approved ("standard")

- approved plan;
- receipts;
- normal fingerprints;
- ordinary checks.

## Reportable

Require stronger evidence:

- frozen approved plan;
- run ID;
- strong input identity;
- code identity;
- complete execution evidence;
- declared outputs;
- deterministic or explicitly unresolved lineage;
- environment capture;
- final verification.

# 6. Provenance rule

The provenance system should move toward explicit edges:

```text
plan
  ↓
run
  ↓
outputs
```

rather than reconstructing relationships from timing.

Preferred hierarchy:

1. workflow-native lineage;
2. run-specific output relationships;
3. before/after fingerprints;
4. timing as fallback only.

Ambiguous timing must produce a gap.

---

# 7. Evaluation rule

Evaluate Extra against its own claims, in two parts:

1. **Execution chain:** the C1 fixture and defect catalog (deterministic; known misses stay until fixed, then invert).
2. **Plan stage:** a small grill-coverage eval. Each scenario has a hidden list of required choices; score coverage,
   sourcing, unnecessary questions and invented facts. Scripted user answers; model and plugin version recorded;
   a lab colleague reviews the hidden lists; scenarios used to design M3 are not used to judge it.

The multi-condition error-reduction study is Track R (optional, `03`).

---

# 8. Data-state rule

No inspector framework. Data-state checks (matrix state including AnnData `X` and layers, identifiers, sample
alignment) are input checks inside `data-contract-check`, read-only, and grown only when a sibling repository's defect
needs one. A missing optional reader (`h5py`, `Rscript`) is a gap.

---

# 9. Review/privacy rule

External model review should be treated as model critique, not independent scientific validation.

Any packet leaving the machine should pass:

```text
packet creation
      ↓
deterministic scan
      ↓
preview
      ↓
explicit user confirmation
      ↓
external reviewer
```

The system should record the packet identity and approval (recording it durably is a user decision; the skill
currently writes no review record).

---

# 10. Release rule

Extra stays 0.x. The target is one researcher and their own lab repositories. Release work (schema freeze, citation
file, DOI, support policy, public users) waits for the user to decide to publish. External provenance formats, if ever
wanted, are exporters, not the internal model.
