## Commits
1. `fix(gate,verify): take the Bash exit status from the hook event (E3c)`
   - **hooks.json:** registers `PostToolUseFailure` (matcher Bash) with the same command and 20 s timeout as `PostToolUse` (`gate_run.py post`).
     - I reused the existing `post` mode, which reads `hook_event_name`. That is the smaller change: no new HANDLERS entry, no usage change, and gate_run.py is untouched.
     - The Codex manifest stays hook-less.
   - **gate.py `exit_status(event)`** returns (status, source, extra fields):
     - An explicit int in tool_response (`exit_code_in`) wins: source `"response"`.
     - `PostToolUse` gives 0, source `"event"`, with three exceptions:
       - `tool_input.run_in_background` true, or a response dict with a `backgroundTaskId`, gives `"unknown"` and `background: true`. The `backgroundTaskId` check is a best-effort guess at the response key.
       - A response with `interrupted: true` gives `"interrupted"`. This is conservative.
     - `PostToolUseFailure`:
       - `is_interrupt` true gives `"interrupted"`.
       - Otherwise a first line `Exit code N` with N != 0 gives N, source `"error"`. `Exit code 0` inside a failure event is treated as `"failed"`, so a failure event is never read as success.
       - Otherwise `"failed"`.
     - Anything else, including a payload with no `hook_event_name`, gives `"unknown"` with source null.
   - **New receipt fields:** `exit_source` (always present), plus `error_line` and `background`.
     - **Error text:** the receipt keeps only `error_line`, which is the error's first line, stripped and cut to 200 characters. The output is never stored. A test checks that later lines are absent.
     - For a bare message such as `Command timed out after 2m 0s`, that first line is kept.
   - **hookSpecificOutput.hookEventName** now echoes the event name, so it says `PostToolUseFailure` on failures.
     - I tried adding ", exit N" to the systemMessage and then removed it, to keep gate output unchanged.
   - **verify.py (run-status branch only):**
     - An int != 0 gives the existing block "failed (exit N)", unchanged.
     - `"failed"` gives the row "failed (no exit code)" and the block "`p` failed without an exit code at T: <error_line>". This is the same block severity as a failed run.
     - `"interrupted"` gives the row "interrupted" and the block "`p` was interrupted at T".
     - 0 with exit_source "event" gives the row "ran (exit 0 from hook event)", with no finding.
     - `background` gives the row "started in the background (exit status unknown)" and a gap.
     - `"unknown"` and legacy null keep the existing gap message ("carried no exit status..."). **Decision:** legacy null stays a gap, not info ("a gap is never clean"). Older gates registered only PostToolUse, so null receipts were probably successes, but the host is not recorded.

## Suggested README/docs text (another workstream owns README.md and docs/*.md)
- docs/approval-gate.md: "The run-receipt hook is registered for both `PostToolUse` and `PostToolUseFailure` (matcher Bash). Claude Code fires `PostToolUse` only after a command succeeds, so its receipt records `exit_status` 0 with `exit_source` `event`; a command started with `run_in_background` has only started, so it is `unknown`. A failed command fires `PostToolUseFailure`: the receipt records N from the error's `Exit code N` first line (`exit_source` `error`), or `failed` when there is none (the shell did not start, or a timeout), or `interrupted`. An exit code in the tool response always wins (`exit_source` `response`). Only the error's first line is kept (`error_line`, at most 200 characters). A payload without an event name is `unknown`. Verify reports a nonzero, failed, or interrupted run as a failure, and an `unknown` (or older null) status as a gap."
- README "run receipts" field list: add `exit_source`, `error_line` and `background`, and say that `exit_status` can be an int, `failed`, `interrupted` or `unknown`. Replace the old suggestion "so `exit_status` is often `unknown`" from e3/NOTES with the event-based text above.
- The old e3/NOTES suggestions about Codex and `sbatch --wrap` `paths`/`job_cwd` still apply.
