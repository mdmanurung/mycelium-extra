## Commits
1. `fix(gate,verify): record a missing exit status as unknown and report it as a gap (E3c)`
   - gate.py: `exit_status()` now returns `"unknown"` when the response carries no status. That covers a string response, no response, and a dict without an exit key. The old recursive search was renamed `exit_code_in`.
   - verify.py (run-status branch only, about line 660): `code == 0` gives "ran". Anything else (`"unknown"`, or `null` in receipts from older gates) gives "ran (exit status unknown)" plus the gap "`<path>` ran at T, but the tool response carried no exit status, so the run is not counted as a success."
   - **Decision:** a plan whose only evidence is an unknown exit gets **CONFORMS_WITH_GAPS**. This is documented in skills/verify/SKILL.md.
   - Sbatch receipts with a job id are excluded from this gap. Their exit status is the submit's, and the job state already comes from sacct (a missing sacct is already a gap). The explore listing now prints "exit unknown".
   - Tests: gate `test_missing_exit_status_is_recorded_as_unknown` covers 5 response shapes. `test_sbatch_receipt` now expects "unknown". Verify `test_unknown_exit_status_is_a_gap` checks the row, the gap text and CONFORMS_WITH_GAPS, does the same for a legacy null receipt, and then checks that a later exit-0 run gives CONFORMS.
2. `fix(gate): resolve sbatch --wrap payloads against -D/--chdir (E3a)`
   - New `job_cwd(tokens, cwd)` handles `-D DIR`, `-DDIR`, `--chdir DIR` and `--chdir=DIR`, relative to the cwd sbatch ran from. analyse_command now analyses wrap payloads from the job folder.
   - classify no longer counts the value of `-D`/`--chdir` as a gated path. This fixes a false deny: `sbatch -D analysis/a --wrap=...` used to require the plan to name the folder.
   - on_post: the sbatch receipt's `paths` now include the payload's gated scripts. Before, a --wrap receipt had `paths: []`, so verify showed "no receipt" for a script run that way. `job_cwd` is added when -D is given.
   - A plan is credited (`plans`) with a --wrap job only if its table also names those scripts.
   - `#SBATCH --chdir`: the gate reads `#SBATCH` lines only to record them (`sbatch_lines`). It does not resolve paths inside a job script, so there is nothing to resolve against it. Not implemented, by design.
   - Test: `test_sbatch_chdir_wrap_runs_in_the_job_folder` checks the 4 forms pass and are receipted as analysis/a/x.py, and that 3 twins deny (wrong -D, -D after --wrap, `../x.py`).

## Not done: (b) Snakemake rule inputs (design for a follow-up)
- verify.py `snakemake_records` builds "command" from shellcmd + code + every `input` entry. `mentions()` then matches planned paths against that string, so any rule input counts as a run.
- Fix: drop `input`. For `script:`/`notebook:` rules, shellcmd is null and `code` is base64 of `pickle_code(run_func.__code__)`. The run function body is `script("<path as written>", "<abs Snakefile dir>", input, ...)`.
- Decode it **without unpickling**: `pickletools.genops` parses opcodes and executes nothing. Running `pickle.loads` on repo files would be a code-execution risk.
- Take the string constants that have a script extension and add each one raw, plus joined to every absolute-directory constant and to the workdir.
- shell: rules keep working, because an input used as `{input.script}` appears in the expanded shellcmd. test_steps_inside_a_snakemake_wrapper relies on that.
- Tests to add: an input-only mention gives "no receipt", and a script: record with a pickled code object gives "ran in Snakemake rule".

## Maintainer decisions / open questions
